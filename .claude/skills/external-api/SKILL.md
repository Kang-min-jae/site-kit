# 외부 API 연동 절차 (스택 무관)

## 1. 먼저 적는다

- 문서 주소, 인증 방식(키를 어디에 넣는지), 하루·분당 한도, 한도 초기화 시각(시간대 포함)
- 오류가 오는 방식 — HTTP 상태 코드로 오는지, **HTTP 200 본문 안의 오류 필드**(예: `error`, `resultCode`, `faultInfo`)로 오는지
- 이용약관: 결과를 저장·캐시·표시해도 되는지, 출처 표시 문구

## 2. 클라이언트 모듈을 하나만 만든다

이 서비스로 가는 모든 호출이 이 모듈 하나를 거친다. 모듈이 맡는 것:

1. 키가 없으면 조용히 건너뛴다(개발 환경).
2. 한도 초과 상태면 초기화 시각까지 부르지 않는다(프로세스 메모리나 공유 캐시에 "멈춤 시각" 저장).
3. 실패 직후 몇 분은 새 호출을 하지 않는다(쿨다운). 이미 캐시된 성공 결과는 계속 쓴다.
4. 타임아웃(예: 10초)을 건다. 연결 실패는 한 번만 다시 시도한다.
5. 성공 판정: HTTP 성공 **그리고** 본문에 오류 필드 없음 **그리고** 해석(JSON·XML) 성공.
6. 실패는 전용 예외로 던진다. 쿨다운·한도 때문에 건너뛴 경우는 하위 예외로 구분해 같은 로그를 반복하지 않는다.
7. 성공만 캐시한다. 캐시 저장은 성공했을 때만 하고, 실패는 예외로 저장을 건너뛴다. 캐시 키에 API 키를 넣지 않는다.
8. 같은 요청이 동시에 오면 진행 중인 호출 하나를 함께 기다린다(single-flight: `키 → 진행 중 작업` 표).

스택별 도구(타임아웃·재시도·캐시·single-flight)는 `STACK_MAPPING.md`를 출발점으로 하고, 설치된 버전의 공식 문서로 확인한다.

## 3. 결과의 의미를 나눈다

- "그런 데이터가 없음" → 빈 값 (404로 처리해도 된다)
- "지금 API를 쓸 수 없음" → 예외 (화면은 이전 값이나 안내 문구, 공용 캐시에는 남기지 않는다)
- 자주 보이는 목록·순위는 DB에 스냅샷으로 저장하고, 실패하면 마지막 성공값을 보여준다. 빈 결과로 덮어쓰지 않는다.

## 4. 확인한다 (mock 서버)

외부 API 주소를 설정으로 mock 서버로 바꿔 세 상황을 재현하고 표로 보고한다(테스트용 설정은 커밋 전에 되돌린다).

| 상황 | 기대 결과 |
|---|---|
| 정상 | 화면 정상, 같은 요청 두 번째부터 외부 호출 0 |
| 한도 초과(HTTP 200 + 오류 본문) | 호출 1~2회 뒤 중지, 404가 캐시되지 않음, 마지막 성공값 표시 |
| 네트워크 오류·타임아웃 | 1회 재시도 뒤 쿨다운, 화면이 멈추지 않음 |
| 동시 요청 10개(캐시 빈 상태) | 외부 호출 1회 |

## 하지 않는다

- HTTP 응답을 통째로 캐시하는 기능(HTTP 클라이언트 캐시, 프레임워크의 fetch 캐시)으로 외부 응답을 캐시하지 않는다 — HTTP 200 오류 본문까지 저장된다.
- 브라우저에서 API 키로 직접 부르지 않는다.
- 공용 캐시 페이지를 만드는 도중에 "요청마다 다른" 외부 호출을 넣을 때는, 프레임워크가 그 페이지를 동적으로 바꾸거나 오류를 내지 않는지 확인한다.
