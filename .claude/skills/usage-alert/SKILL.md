# 사용량 경고 대응 절차 (스택 무관)

## 1. 상황 정리 (먼저 확인)

- 어떤 항목이 몇 % / 한도 / 초기화 날짜 / 하루 증가량 → 며칠 버틸 수 있는지 계산한다.
- 최근 바뀐 것: 배포, 새 기능, 봇 트래픽(로그의 규칙적인 요청), 개발 서버·스크립트·미리보기 배포의 운영 DB 사용.

## 2. 측정 (운영 DB 금지)

- 운영과 비슷한 규모의 데이터를 로컬 DB에 만든다.
- DB 앞에 바이트를 세는 중계기를 두거나 쿼리 통계(Postgres `pg_stat_statements`, MySQL `performance_schema`)로 화면·API별 DB 전송량과 반환 행 수를 잰다.
- 외부 API는 mock 서버로 호출 수를 센다. 서버 실행 수는 캐시 적중 여부로 센다.
- 결과를 표로: 화면/요청 | 1건당 비용 | 하루 횟수(추정) | 하루 합계.

## 3. 흔한 원인 (이 순서로 의심)

1. 사용자마다 다르지 않은 화면이 요청마다 생성됨(레이아웃에서 로그인 정보 읽기, 비로그인에게 세션 쿠키 발급).
2. 목록이 행 전체·큰 JSON 열을 읽음, 프로그램에서 거르기, N+1, 저장 후 전체 행 반환.
3. 봇이 서로 다른 페이지를 계속 엶(캐시가 소용없음) → User Agent 확인 후 차단.
4. 개발 서버·스크립트·미리보기 배포가 운영 DB를 씀.
5. 넓은 캐시 무효화(전체 삭제)로 재계산이 몰림.
6. 실패가 캐시되지 않아 요청마다 외부 API 재시도(또는 실패가 캐시되어 데이터가 사라짐).

## 4. 고치기와 보고

- 가장 큰 원인부터 하나씩 고치고 같은 방법으로 다시 잰다.
- 배포 없이 바로 할 수 있는 조치(방화벽 봇 차단, 환경 변수 범위 조정, 개발 서버 끄기)를 먼저 알려 준다.
- 수정 전후 숫자, 남은 위험, 배포 후 확인할 그래프를 보고한다. 수정은 묶어서 한 번에 배포한다.
