# 배포 전 점검 절차 (스택 무관)

1. **품질 검사**: 린트, 타입 검사, 테스트, 빌드. 하나라도 실패하면 멈추고 출력과 함께 보고한다.
2. **화면 종류**: 빌드·라우트 목록에서 정적 / 주기적 재생성 / 요청마다 생성이 의도대로인지. 공용 화면이 실수로 "요청마다"가 되지 않았는지.
3. **캐시 동작**(로컬 운영 모드 실행, 로컬 DB):
   - 비로그인으로 공용 화면을 두 번 받는다 → 캐시 MISS → HIT(또는 같은 생성 시각), 응답 헤더에 공유 캐시 수명(`s-maxage` 등).
   - 비로그인 응답에 `Set-Cookie`(세션 쿠키)가 없는지.
   - 로그인 쿠키로 같은 주소를 받는다 → `private, no-store`, 내 정보가 보인다.
   - 공용 응답 본문에 사용자별 정보(닉네임, 내 평점, 관리자 메뉴 등)가 없는지 검색한다.
4. **권한**: 이번에 추가·변경한 쓰기 요청이 서버에서 로그인·권한·입력값을 확인하는지.
   **보안 헤더**: 응답에 CSP·HSTS·nosniff·Referrer-Policy가 있는지(처음 붙였다면 빠지지 않았는지).
   **화면**: `design/`가 있으면 `node scripts/design-lint.mjs`(출시·납품이면 `--release`)를 돌리고, 바뀐 화면을 `node scripts/shoot.mjs`로 375·1440 캡처해 **직접 본다**(접근성 자동 검사 결과 포함). 그다음 `design-review`.
   **소재**: 새로 넣은 글꼴·사진·음원·샘플의 출처·라이선스가 CREDITS에 있는지, 글꼴 파일을 배포하면 라이선스 전문이 옆에 있는지.
   **작은 사이트**(AGENTS.md 20장): 요청마다 서버가 도는 화면이 0개인지, 종량제 이미지 변환을 쓰지 않는지, 구조화 데이터의 가게 정보가 화면과 같은지.
5. **사용량 영향**: 요청 1건당 서버 실행·DB 전송 바이트·외부 API 호출이 늘었는지. 늘었다면 숫자와 이유.
6. **운영 DB 보호**: 테스트에 운영 DB를 쓰지 않았는지, 비밀 값·`.env`가 diff에 없는지.
7. **묶어서 한 번에**: 커밋 메시지에 무엇을·왜·어떻게 확인했는지 적고 한 번만 배포한다.
8. **배포 후 볼 것**을 알려 준다: 확인할 로그 메시지, 캐시 적중, 사용량 그래프.
